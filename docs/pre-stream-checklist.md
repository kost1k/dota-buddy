# Чеклист выезда на игровой ПК

Первый запуск всей связки на машине с Dota 2 и Streamlabs. Топология (a):
репозиторий разворачивается там же, всё локально через `127.0.0.1`.

## 1. Поднять приложение

```bash
bun install
cp .env.example .env
bun run build
bun run preview
```

Именно `build` и `preview`, а не `dev`: режим разработки держит
пересборку и HMR, которые на трёхчасовом стриме не нужны и стоят кадра.

В `.env` для первого прогона:

```
NUXT_GSI_SECRET=
NUXT_LOG_LEVEL=debug
NUXT_GSI_RECORD=C:/dota-buddy/session.jsonl
```

Пустой секрет отключает проверку — на первом прогоне это на одну причину
отказа меньше. `debug` покажет в консоли каждое выведенное событие.

**`NUXT_GSI_RECORD` заполнить обязательно.** Это единственный способ
привезти реальные данные обратно; без него всё увиденное останется там.

Про путь: косые прямые, а не обратные — в `.env` обратный слэш легко
налетает на экранирование, а Node на Windows прямые понимает. **Директория
должна существовать**, файл создастся сам. Файл ДОПИСЫВАЕТСЯ, так что
несколько прогонов склеятся в один; меняй имя, если нужно разделить.

При старте сервер печатает одну из двух строк:

```
[recorder] пишу сырые пакеты в C:/dota-buddy/session.jsonl
[recorder] ЗАПИСЬ НЕ РАБОТАЕТ (...): ENOENT ...
```

Если видишь вторую — чинить сразу, иначе выяснится по возвращении без
файла, когда переснять уже нельзя.

Размер: пакет примерно раз в секунду, в конфиге включены все блоки данных.
За матч наберутся десятки мегабайт. Это нормально — блоки нужны, чтобы
ответить, доходит ли `events`.

Проверка: `GET /api/health` отвечает `status: "ok"`.

## 2. Подключить Dota

1. Скопировать [`docs/examples/gamestate_integration_dota_buddy.cfg`](examples/gamestate_integration_dota_buddy.cfg)
   в `...\Steam\steamapps\common\dota 2 beta\game\dota\cfg\gamestate_integration\`
2. В файле: `uri` — `http://127.0.0.1:3000/api/gsi`, `token` — пустой или
   совпадающий с `NUXT_GSI_SECRET`
3. В параметры запуска Dota 2 добавить `-gamestateintegration`
4. Запустить бот-матч

Проверка: в консоли сервера при `debug` идут строки `[gsi]`.

## 3. Подключить Streamlabs

Browser Source на `http://localhost:3000/`, размер 1920×1080.

- **«Enable Browser Source Hardware Acceleration» — включено.** С
  выключенным каждый кадр 1080p стоит ~7.9 МиБ трафика CPU↔GPU.
- **«Use custom frame rate» — выключено.** По умолчанию страница залочена
  на выходной клок OBS, что и даёт ощущение 60 fps без рассинхрона.

## 4. Что смотреть

- Бадди реагирует на происходящее: просел при смерти, взвинтился под
  уроном, потеплел на килстрике
- Реакция на одно и то же событие каждый раз выглядит иначе
- Повторы слабеют, после затишья бьют снова в полную силу
- Смена сцены в OBS не роняет сервер и не сбрасывает состояние матча

## 5. Замеры, ради которых всё это (тикет 11)

- **Доходит ли блок `events` до обычного игрока.** Смотреть в записи: есть
  ли в теле пакетов ключ `events`. От ответа зависит, возможен ли таймер
  Рошана в принципе.
- **Реальная задержка «событие в игре → POST».** Считать по
  `provider.timestamp` и `map.clock_time` против поля `at` в записи.
- **Даёт ли `fpsLimit = 12` во сне реальные 12 кадров.** На машине
  разработки не измеряется: панель браузера скрыта и `rAF` придушен.

## 6. Привезти

Файл записи. Он воспроизводится на машине разработки и становится
регрессионным материалом.

## Известные ограничения первого прогона

- **Воспроизведения записи ещё нет** (тикет 10) — файл пишется, но
  проигрывать его пока нечем.
- **Приёмка альфы отдельно** — краевые и полупрозрачные приёмы проверяются
  тест-картой [`obs-alpha-probe.html`](examples/obs-alpha-probe.html),
  а не на живом бадди.
