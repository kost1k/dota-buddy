# ADR-0002. События выводятся на сервере, аффект считается на клиенте

- **Статус:** принято
- **Дата:** 2026-09-19

## Контекст

Разведка по GSI (`docs/research/gsi-data-surface.md`) установила два факта,
определяющих архитектуру:

1. **Нативных событий всего шесть** (`roshan_killed`, `aegis_picked_up`,
   `aegis_denied`, `courier_killed`, `bounty_rune_pickup`, `tip`). Всё
   остальное — первая кровь, смерть, респавн, байбек, покупка предмета,
   взятие таланта, аганим, шард, уровень — выводится **сравнением соседних
   снапшотов**, то есть требует памяти о предыдущем состоянии.
2. **Каденция — порядка 1 Гц** (теоретический потолок ~10 Гц, на практике в
   открытом баг-репорте Valve наблюдают 1 пакет в секунду).

В прототипе обе задачи решались на клиенте: `app.vue` держал `lastStats` и
диффил их в обработчике WebSocket-сообщения.

Проблема в том, что **browser source в OBS перезагружается**: при смене
сцены, при `Refresh browser`, при падении процесса, при включении
«Shutdown source when not visible». Каждая перезагрузка обнуляет память
клиента, и бадди забывает, что стример уже умирал, уже брал аганим, уже
разгонялся.

## Решение

Граница проходит между «что случилось» и «что бадди сейчас чувствует».

**Сервер (Nitro):**

- хранит предыдущий снапшот и выводит из него нормализованный поток событий;
- владеет счётчиками матча, от которых зависит приглушение веса по частоте;
- транслирует клиенту готовые события, а не сырые снапшоты;
- отвечает на `POST /api/gsi` **до** рассылки по WebSocket — `throttle`
  отсчитывается от момента ответа, поэтому задержка обработчика складывается
  с интервалом опроса.

**Клиент:**

- интегрирует оси аффекта по `rAF` между пакетами, применяя инерции из
  ADR-0001;
- тикает локально всё, что обязано идти непрерывно: таймер респавна,
  кулдауны, тренды;
- остаётся чистым рендером состояния, не источником истины о матче.

## Последствия

**Хорошее.** Оверлей переживает перезагрузку источника в OBS без потери
контекста матча. Логика вывода событий тестируется на сервере без браузера.
Серверное хранение снапшотов даёт готовую основу для отложенной сводки
сессии, не требуя отдельной работы. Плавность не зависит от каденции GSI:
пакет — ключевой кадр, промежуток интерполируется клиентом.

**Плохое.** Появляется серверное состояние, которое нужно уметь сбрасывать
на границе матча, иначе счётчики частоты протекут между играми. Два места
вместо одного: событие надо провести через сервер, даже когда быстрее было бы
посчитать на клиенте.

**Риск.** Клиент подключается в середине матча и не знает накопленного
состояния (вехи, счётчики частоты). Лечится снимком состояния при
подключении — заложить в протокол сразу, дешевле, чем добавлять потом.
