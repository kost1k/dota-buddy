# 16. Протокол оверлея должен держаться с обеих сторон

Status: done
Type: task

## Зачем

`shared/overlay-message.ts` объявляет `OverlayMessage` и разбирает его на
приёме — `parseOverlayMessage` типизирован и покрыт тестом. Отправляющая
сторона не типизирована ничем:

```ts
// server/utils/ws.ts:19
broadcast: (message: unknown) => { /* ... */ }
```

`unknown` стирает контракт ровно на том шве, ради которого модуль
существует. Переименованное на сервере поле скомпилируется, уйдёт в сокет и
будет молча отброшено на клиенте через `default: return null`. Отказ
беззвучный: оверлей просто перестанет получать этот вид сообщений.

Отправителей три — `ingest.ts:32,40,42`, и все три пишут литералы, которые
никто не сверяет с типом.

### Утечка через шов

```ts
// server/routes/ws.ts:12
peer.send(JSON.stringify({ type: 'sync', snapshot: matchState.snapshot() }))
```

Это единственное место в коде, которое зовёт `peer.send` мимо `wsService`, —
и тем теряет обе защиты, которые тот модуль описывает на десять строк:
`try/catch` и обработку отклонённого промиса. Комментарий там же объясняет,
почему одного мало: при оборванном сокете `peer.send` не бросает, а
возвращает промис, который отклоняется, и это валит процесс необработанным
отказом. В эфире это не мелочь — OBS перезагружает browser source при каждой
смене сцены, то есть сокеты рвутся штатно и постоянно.

Хуже того, отправка идёт пиру, который только что подключился, — то есть
ровно в тот момент, когда сокет с наибольшей вероятностью ещё нестабилен.

### Защита не проверена ничем

Отдельного теста на `wsService` нет. Поддельный пир в `test/ingest.test.ts:20`
возвращает `undefined`, то есть не задевает ни `try/catch`, ни отклонённый
промис. Причина существования модуля не покрыта.

## Что делаем

| Где | Что меняется |
| --- | --- |
| `server/utils/ws.ts` | `broadcast(message: OverlayMessage)` вместо `unknown` |
| `server/utils/ws.ts` | новый `send(peer, message: OverlayMessage)` с теми же двумя защитами; `broadcast` становится циклом над ним |
| `server/routes/ws.ts` | `sync` уходит через `wsService.send` |
| `test/ws.test.ts` | новый |

### Один тип, а не второй словарь

Рассматривались именованные методы — `wsService.state(snapshot)`,
`.event(e)`, `.idle()`. Отвергнуто: они заводят второй словарь для тех же
четырёх видов сообщений, которые `OverlayMessage` уже именует. Это ровно то
дублирование, за которое досталось `useReplay` с его шестью псевдонимами над
`ReplayCommand`. При сужении параметра учить нужно один тип, и этот тип уже
существует и уже обслуживает приём.

### Транспорт не узнаёт про домен

Рассматривался `wsService.welcome(peer)`, который сам знал бы, что при
подключении шлётся `sync` с текущим снапшотом. Отвергнуто: это затягивает
состояние матча в транспортный модуль, который сейчас про домен не знает
ничего и правильно делает. `wsService` — это множество пиров и безопасная
отправка; снапшот достаёт роут.

### Тест утверждает наблюдаемое

Три поддельных пира: бросающий, возвращающий отклонённый промис, живой.
Утверждаем, что мёртвые выброшены из набора, а живой получил сообщение, —
удаление из набора и есть след того, что отказ перехвачен. Это утверждение о
значении, а не о том, чего не случилось.

Перехват `unhandledRejection` на процессе отвергнут: процессная машинерия
ради того же самого, и она же способна поймать чужой отказ из соседнего
теста. Страховка достаётся даром — убери защиту, и отказ всплывёт, а vitest
сообщит.

## Что НЕ делаем

- **`IngestResult` не сужаем.** Его поле `snapshot` в production не читает
  никто, а воспроизведение выбрасывает результат целиком (`replay.ts:260`),
  но это возвращаемое значение приёмного модуля, а не то, что уходит в
  сокет. Другой шов, другая работа.
- **`createLogger` в трёх обработчиках `routes/ws.ts` не трогаем.** Логгер
  строится заново на каждое событие сокета по всему серверу одинаково — это
  общий вопрос к `createLogger`, и решать его надо целиком или никак.
- **Глоссарий не трогаем.** Нового понятия не вводится, `OverlayMessage` в
  коде уже есть.
