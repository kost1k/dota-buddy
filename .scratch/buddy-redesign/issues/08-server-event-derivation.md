# 08. Серверный вывод событий из снапшотов

Status: done
Type: task
Blocked by: 07

## Зачем

Нативных событий у GSI всего шесть, и доходят ли они до обычного игрока —
не подтверждено. Всё остальное выводится **сравнением соседних снапшотов**,
то есть требует памяти о предыдущем состоянии.

Память обязана жить на сервере: browser source в OBS перезагружается при
смене сцены, при `Refresh browser`, при падении. Клиентский диффинг терял
бы контекст каждый раз, и бадди забывал бы, что стример уже умирал.

## Что сделать

1. Хранение предыдущего снапшота на сервере.
2. Вывод событий диффом: смерть, респавн, убийство, новый уровень, аганим,
   шард, байбек, килстрик.
3. Перенос **свежести** на сервер — сейчас она на клиенте и не переживает
   перезагрузку источника, хотя это состояние матча (Q35).
4. Сброс состояния на границе матча: по смене `matchid` и по переходу
   `game_state`.
5. Снимок состояния при подключении клиента — иначе подключившийся в
   середине матча не знает ни уровня, ни вех.
6. Протокол WebSocket отдаёт **и события, и состояние**: события нужны
   реакциям, непрерывное состояние — осям аффекта.

## Критерий приёмки

- [ ] Каждое событие выводится тестом на паре снапшотов
- [ ] Перезагрузка страницы не сбрасывает свежесть, уровень и вехи
- [ ] Смена матча сбрасывает всё
- [ ] Повторный одинаковый снапшот не порождает событий

## Comments

### Реализовано — 2026-09-20

Вывод событий диффом вынесен в чистую функцию (`#shared/derive`) и
покрыт тестами на парах снапшотов. Серверное состояние — память,
свежесть и счётчик событий — живёт в `server/utils/match-state.ts`.

Протокол WebSocket переписан: `sync` при подключении, `state` на каждое
обновление, `event` на каждое выведенное событие, `idle` при пустом
payload. Состояние идёт **перед** событием: событие описывает изменение, и
клиент должен увидеть новое положение прежде, чем ему скажут, что
произошло.

### Упрощение, найденное по дороге

**Вехи и уровень отдельно не передаются** — они поля снапшота
(`aghanims_scepter`, `aghanims_shard`, `level`), и клиент выводит их
оттуда. Первая редакция копила их параллельно и досылала в `sync`; это
лишнее состояние, которое пришлось бы сверять. Выведенное из снапшота верно
по построению и самовосстанавливается при перезагрузке.

### Проверено сквозным прогоном

Два прогона сценария «смерть и респавн», затем **перезагрузка страницы**,
затем третий прогон:

| | вес респавна | id события |
| --- | ---: | ---: |
| первый прогон | 0.25 | 2 |
| второй прогон | — | 6 |
| после перезагрузки | **0.108** | **8** |

Вес упал, счётчик продолжился — **свежесть пережила перезагрузку**, то есть
выполнено главное требование ADR-0002. Смертей 3 → 4, границу матча не
сработало.

### Попутная правка пульта

Пульт после перезагрузки подхватывает состояние с сервера, а не начинает с
нуля. Без этого счётчики матча откатывались назад, сервер справедливо
считал это новым матчем и сбрасывал свежесть — то есть перезагрузка пульта
незаметно обнуляла ровно то, что на ней и проверяется.

Обнаружение границы при этом работает верно: кнопка «Сброс» откатывает
счётчики намеренно, и сервер это ловит.

### Что осталось

Оси аффекта пока двигают только события. Непрерывная подпитка от здоровья,
счёта и дебаффов — тикет 09, теперь разблокированный: данные до клиента
доходят.
